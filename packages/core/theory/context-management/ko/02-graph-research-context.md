# 그래프로 조사 컨텍스트를 정제하는 방법

[목차](README.md) · [English](../02-graph-research-context.md)

## 자료가 많다고 이해가 좋아지는 것은 아니다

문제를 이해하려면 자료가 필요하다. 문서, Wiki, 코드, 검색 결과와 과거 기록은 모두 중요한 원본이다.

그러나 원본을 많이 넣는 것과 좋은 조사 컨텍스트를 만드는 것은 다르다. Context Window가 커져도 모델이 그 안의 모든 내용을 같은 수준으로 활용하는 것은 아니다. 핵심 정보는 중복, 오래된 설명과 주변 자료 사이에서 경쟁한다.

```text
Context Window
= 넣을 수 있는 정보의 최대 크기

Effective Context
= 현재 판단에 실제로 도움이 되는 작업 입력
```

따라서 조사 컨텍스트의 목표는 가능한 많은 문서를 모으는 것이 아니다. 현재 질문에 필요한 사실과 관계를 높은 밀도로 구성하는 것이다.

## 문서에는 노이즈가 섞일 수밖에 없다

문서는 하나의 질문에만 답하기 위해 작성되지 않는다. 지식을 보존하고, 배경을 설명하고, 서로 다른 독자가 이해할 수 있도록 만든다.

그래서 좋은 문서에도 다음 내용이 자연스럽게 함께 들어간다.

- 배경과 역사
- 이해를 돕는 예시
- 반복과 요약
- 문맥을 연결하는 문장
- 다른 독자를 위한 부연 설명
- 현재 질문과 관계없는 세부 사항

이 내용들은 문서에서는 필요하다. 하지만 특정 질문에 답하는 순간에는 일부가 노이즈가 된다.

> 문서가 나쁜 것이 아니다. 문서의 목적과 현재 LLM 컨텍스트의 목적이 다르다.

같은 문장도 질문에 따라 핵심이 되거나 노이즈가 될 수 있다. 그러므로 문서 전체를 그대로 넣는 방식으로는 모든 질문에 맞는 깨끗한 컨텍스트를 만들기 어렵다.

## Wiki, Tree와 일반적인 RAG

기존 방식은 각각 중요한 문제를 해결한다.

### Wiki: 문서와 페이지를 보존한다

Wiki는 사람이 지식을 작성하고 탐색하기에 좋다. 페이지 사이에 링크도 있다. 그러나 링크가 의존, 구현, 변경, 반박 중 어떤 관계를 의미하는지는 본문을 읽어야 아는 경우가 많다.

Wiki의 기본 단위는 여전히 문서와 페이지다.

### Tree: 하나의 계층을 보여준다

Tree는 상위와 하위, 분류와 항목의 관계를 명확하게 표현한다. 하지만 현실의 하나의 대상은 여러 정책, 기능, 파일과 동시에 연결된다. 하나의 부모-자식 계층만으로는 이런 다대다 관계를 표현하기 어렵다.

### 일반적인 RAG: 비슷한 청크를 찾는다

RAG는 질문과 의미적으로 비슷한 문서 청크를 찾아 전체 문서를 넣는 비용을 줄인다.

```text
질문
→ 관련 청크 A
→ 관련 청크 B
→ 관련 청크 C
```

그러나 검색 결과가 독립적인 텍스트 조각이라면 LLM은 다시 관계를 추론해야 한다.

- A와 B가 같은 대상을 말하는가?
- 어느 것이 원인이고 어느 것이 결과인가?
- 어떤 정책이 어떤 구현에 적용되는가?
- 여러 청크가 충돌한다면 무엇이 현재 상태인가?

RAG는 관련 문장을 찾지만, 관련 문장이 어떻게 연결되는지를 항상 제공하지는 않는다.

## 그래프에서는 관계가 정보가 된다

그래프는 개체와 관계를 기본 단위로 사용한다.

```text
[기능 A] ──적용받음──> [정책 B]
[기능 A] ──구현됨────> [파일 C]
[기능 A] ──의존함────> [기능 D]
[변경 E] ──수정함────> [기능 A]
```

문서의 문장 속에 들어 있던 관계의 종류와 방향이 명시적인 정보가 된다.

그래프가 단순히 링크를 하나 더 붙이는 것처럼 보일 수 있다. 중요한 차이는 그 관계가 부가 설명이 아니라 검색과 조립의 기준이 된다는 점이다.

## 검색 결과 자체가 관계도가 된다

일반 검색의 결과는 관련 자료의 목록이다. 그래프 검색의 결과는 질문과 관련된 개체가 서로 연결된 서브그래프다.

```text
             [정책 B]
                 ↓ 적용
[변경 E] → [기능 A] → [파일 C]
                 ↓ 의존
             [기능 D]
```

이 결과는 이미 다음을 포함한다.

- 질문의 중심이 되는 개체
- 함께 고려해야 하는 주변 정보
- 관계의 종류와 방향
- 탐색한 범위
- 다른 원문으로 돌아가는 경로

즉, 그래프 검색은 관련 정보를 가져오는 동시에 그 정보를 이해하기 위한 구조도 가져온다.

> 일반 검색은 관련 내용을 반환한다. 그래프 검색은 관련 내용이 어떻게 연결되는지까지 반환한다.

## 관계도는 두 번 압축된다

그래프의 압축은 단순히 글자 수를 줄이는 것이 아니다. 설명에 필요한 관계를 보존하면서 주변 서술을 제거하는 압축이다.

첫 번째는 **표현 압축**이다.

```text
문서에 흩어진 설명
→ 개체와 관계
```

두 번째는 **질의 압축**이다.

```text
전체 그래프
→ 현재 질문에 필요한 서브그래프
```

그래서 전체 흐름은 다음과 같다.

```text
문서·코드·기록
  ↓ 개체와 관계 추출
Graph
  ↓ 질문과 관련된 관계 탐색
Subgraph
  ↓ 자연어로 재구성
정제된 조사 Context
  ↓
LLM
```

## 관계도를 다시 글로 만든다

LLM이 최종적으로 사용하기 좋은 형식은 자연어다. 따라서 그래프를 그대로 던지는 것이 목적은 아니다.

예를 들어 그래프에서 다음 관계를 찾았다고 하자.

```text
기능 A → 정책 B의 적용을 받음
기능 A → 파일 C에 구현됨
파일 C → 기능 D에서도 사용됨
변경 E → 기능 A의 현재 동작을 수정함
```

이를 질문에 맞춰 다음과 같이 구성할 수 있다.

> 기능 A는 정책 B의 적용을 받으며 파일 C에 구현되어 있다. 파일 C는 기능 D에서도 사용되므로 수정 시 D에 대한 영향도 확인해야 한다. 현재 동작은 변경 E 이후의 상태를 기준으로 판단한다.

원본 문서 전체는 들어가지 않았지만 판단에 필요한 관계는 남아 있다. LLM은 흩어진 청크에서 구조를 처음부터 추측하는 대신, 이미 정리된 사고 재료를 바탕으로 문제에 집중할 수 있다.

## 그래프는 원문을 대체하지 않는다

그래프도 틀리거나 오래될 수 있다. 관계가 없다고 해서 실제 관계가 없다는 뜻도 아니다.

따라서 그래프는 진실 그 자체보다 **압축된 관계 인덱스**로 사용하는 편이 안전하다.

```text
그래프에서 관련 관계 탐색
→ 필요한 현재 원문 확인
→ 판단
→ 오래된 관계가 있다면 갱신
```

Wiki와 문서는 원본을 보존하고, RAG는 관련 텍스트를 찾으며, 그래프는 관계를 따라 조사 범위를 구성한다. 이 방식들은 서로 완전히 배타적이지 않다. 그래프 기반 검색도 넓게 보면 RAG의 한 형태다.

그래프를 사용하는 이유는 모든 상황에서 항상 우월하기 때문이 아니다. 문서와 기능, 정책과 구현처럼 여러 관계를 함께 복원해야 하는 작업에서 더 작은 조사 컨텍스트를 만들기 유리하기 때문이다.

## 결론

> 그래프 검색의 결과는 단순한 문서 목록이 아니라 이미 압축된 관계도다. 이 관계도를 질문에 맞는 글로 다시 구성하면 적은 토큰으로 더 높은 밀도의 의미를 전달할 수 있다.

정제된 조사 결과는 이제 계획의 입력이 된다. 다음 글에서는 [계획을 만든 전체 과정이 아니라 확정된 계획만 실행에 넘기는 방법](03-save-load-plan-context.md)을 설명한다.
