# 실행 기록이 아니라 현재 상태를 이어가는 방법

[목차](README.md) · [English](../04-save-load-execution-state.md)

## 실행이 길어질수록 과정이 쌓인다

작업을 실행하면 많은 기록이 만들어진다.

- 도구 호출과 작업 로그
- 실패와 재시도
- 실행자의 중간 추론
- 이미 끝난 작업에 대한 설명
- 과거 체크포인트
- 결과를 만들기 위한 임시 파일과 대화

이 기록은 오류를 추적하거나 과거를 감사할 때 유용하다. 그러나 현재 상태를 판단하고 다음 작업을 선택하는 기본 컨텍스트에 모두 넣으면 진행할수록 노이즈가 커진다.

긴 작업을 이어간다는 것은 모든 과정을 계속 기억하는 것과 같지 않다.

## 실행 기록과 현재 상태는 다르다

```text
Execution History
≠
Current Execution State
```

현재 판단에 필요한 것은 대개 다음과 같다.

- 처음 계획과 비교해 무엇이 달라졌는가
- 직전 판단 이후 무엇을 만들었는가
- 현재 결과가 성공 조건을 얼마나 만족하는가
- 계획에서 벗어난 중요한 변경은 무엇인가
- 그 결과를 직접 확인할 수 있는 근거는 무엇인가

반대로 누가 어떤 도구를 몇 번 호출했고 어떤 문장을 생각했는지는 필요할 때 찾아볼 수 있는 기록으로 남겨도 된다. 항상 현재 컨텍스트에 있을 필요는 없다.

## 상태를 Save한다

실행을 이어가기 위해 관찰 가능한 상태를 저장한다.

이를 표현하는 한 가지 방법으로 시작 상태, 이전에 받아들인 상태와 현재 상태를 나눠볼 수 있다.

```text
S0    = 작업 시작 상태
Sprev = 이전 체크포인트에서 받아들인 상태
Scur  = 현재 실행 상태
```

세 상태가 있으면 전체 실행 기록을 다시 읽지 않고도 두 가지 변화를 볼 수 있다.

```text
diff(S0, Scur)
= 처음부터 현재까지의 누적 변화

diff(Sprev, Scur)
= 직전 체크포인트 이후 만들어진 변화
```

누적 변화는 전체 방향과 범위가 유지되고 있는지 보여준다. 직전 변화는 현재 작업이 실제로 무엇을 만들었는지 보여준다.

상태는 코드 차이일 수도 있고, 문서의 새 버전, 데이터 상태, 디자인 결과, 실행 가능한 산출물일 수도 있다. 중요한 것은 작업 서술이 아니라 실제로 관찰할 수 있는 결과를 기준으로 삼는 것이다.

## 중요한 변경의 이유와 근거를 붙인다

상태 차이만으로 모든 판단이 가능한 것은 아니다. 계획에 직접 적혀 있지 않은 중요한 변경이 있다면 왜 바뀌었는지와 무엇으로 확인할 수 있는지를 함께 제공해야 한다.

```text
현재 판단 입력
= 누적 상태 변화
+ 이번 작업의 상태 변화
+ 중요한 변경의 이유
+ 직접 확인할 수 있는 근거
```

여기서 이유는 실행자의 긴 자기 설명이 아니다. 현재 계획만으로 설명되지 않는 중요한 변화가 왜 필요했는지를 짧고 출처와 연결된 형태로 남기는 것이다.

## 깨끗한 계획 기준을 Load한다

실행 중인 LLM은 자신의 작업 과정을 가장 많이 알고 있다. 그만큼 자신의 선택을 그럴듯하게 설명하기도 쉽다.

따라서 체크포인트 판단은 실행 서술에만 맡기지 않는다. 앞 단계에서 만든 깨끗한 계획 기준을 다시 불러오고, 현재 상태의 변화와 근거만 결합한다.

```text
깨끗한 계획 기준 Load
+ diff(S0, Scur)
+ diff(Sprev, Scur)
+ 중요한 변경 이유와 근거
= 체크포인트 판단 컨텍스트
```

이 구조는 실행자가 틀렸다고 가정하는 것이 아니다. 계획을 판단하는 컨텍스트와 실행 과정을 만든 컨텍스트를 분리해, 결과를 원래 목표에 다시 연결하는 방법이다.

## 판단 결과는 작아야 한다

체크포인트의 목적은 새로운 긴 보고서를 만드는 것이 아니다. 다음 행동을 결정하는 것이다.

예를 들어 판단 결과를 다음처럼 작게 구분할 수 있다. 이름과 개수는 구현에 따라 달라질 수 있다.

```text
계속 진행
결과 또는 실행 수정
중요한 사용자 결정 요청
전체 결과 완료
현재 조건 안에서 진행 실패
```

판단 결과에는 필요한 결정, 짧은 이유와 다음 위치만 남긴다. 실행 컨텍스트는 그 결정을 받아 다음 작업을 수행한다.

```text
실행
  ↓ 상태 Save
깨끗한 계획 기준에서 검토
  ↓ 결정
실행 컨텍스트가 결정 Load
  ↓
다음 실행
```

이렇게 하면 검토 과정 자체도 다음 실행에 불필요하게 누적되지 않는다.

## 계획이 잘못되었다면 실행만 고치지 않는다

현재 결과의 문제가 단순한 실행 오류라면 같은 계획 안에서 수정할 수 있다. 그러나 성공하려면 목표, 주요 구조나 중요한 제약을 바꿔야 한다면 계획 단계로 돌아가야 한다.

```text
실행 문제
→ 같은 계획에서 수정

계획 문제
→ 새 계획 확정
→ 새 실행 기준 구성
→ 실행 컨텍스트 교체
```

이 구분이 없으면 실행 컨텍스트가 계획을 조금씩 고치며 사실상 새로운 방향을 만들 수 있다. 그러면 원래 계획과 현재 행동의 관계가 흐려진다.

## HEAD 설계에서 볼 수 있는 예시

다음은 이 이론을 HEAD의 Save/Load 설계에 적용해 표현한 개념 예시다. 세부 체크포인트 계약은 아직 발전할 수 있으며, 이 표기가 현재 구현 프로토콜을 고정하지는 않는다.

- `A`: 깨끗한 문제 인식과 확정된 계획을 가진 판단 기준
- `B`: A가 확정한 horizon을 정확히 실행하는 컨텍스트
- Frozen Wave aggregate와 실제 artifact: worker 보고와 현재 실행 상태를 담은 근거
- 체크포인트: active `A`의 fresh review fork가 내리는 정본 판단

```text
실행 B
  ↓ 정확한 frozen_wave horizon
worker aggregate와 실제 artifact reference 생성
  ↓
active 계획 기준 A를 자동 Load해 검토
  ↓
계속 | 수정 | 사용자 결정 | 완료 | 실패
  ↓
B가 A review가 확정한 다음 horizon을 실행
```

구체적인 저장 형식과 체크포인트 프로토콜은 구현에 따라 달라질 수 있다. 이론의 핵심은 실행 기록 전체를 현재 컨텍스트로 유지하지 않고, 계획 기준과 관찰 가능한 상태를 분리해 필요할 때 다시 조립한다는 데 있다.

## 작은 작업에는 작은 구조를 사용한다

모든 작업에 상태 스냅샷과 정식 체크포인트가 필요한 것은 아니다. 한 번에 끝나는 작은 작업은 현재 결과를 직접 확인하는 것으로 충분하다.

Save/Load 구조가 유용해지는 경우는 다음과 같다.

- 작업이 여러 컨텍스트 윈도를 넘는다.
- 여러 결과가 의존 관계를 가진다.
- 실행과 판단을 분리할 필요가 있다.
- 중단 후 정확한 위치에서 복구해야 한다.
- 잘못된 방향으로 계속 진행할 비용이 크다.

구조의 목적은 의식을 늘리는 것이 아니라, 긴 작업에서도 현재 판단 컨텍스트를 작고 정확하게 유지하는 것이다.

## 결론

> 실행을 이어간다는 것은 모든 과정을 기억하는 것이 아니다. 현재 상태를 Save하고, 깨끗한 계획 기준에서 다음 행동을 다시 판단한 뒤, 필요한 결정만 실행에 Load하는 것이다.

네 단계는 여기서 하나의 흐름으로 완성된다.

```text
필요한 지침만 불러온다
→ 필요한 지식과 관계만 가져온다
→ 확정된 계획만 실행 기준으로 만든다
→ 현재 상태와 필요한 결정만 이어간다
```

LLM 컨텍스트 관리는 더 많이 기억시키는 기술이 아니다. 다음 판단에 필요한 것을 더 깨끗하게 보이게 하는 기술이다.
