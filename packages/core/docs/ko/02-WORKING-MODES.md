# HEAD가 일하는 세 가지 방식

HEAD는 모든 요청을 같은 방식으로 처리하지 않는다. 현재 목표를 이해한 뒤, 결과를 가장 일관되게 만들 수 있는 **가장 작은 작업 방식**을 선택한다.

기본 방식은 세 가지다.

1. HEAD가 한 흐름에서 직접 처리한다.
2. 독립된 결과 하나를 Agent에게 맡긴다(Delegate).
3. 합의된 계획을 여러 단계로 실행한다(Run).

이 선택은 단순히 작업이 길거나 어려운지, 사용할 수 있는 Agent가 있는지로 결정하지 않는다. **전체 맥락과 실행이 얼마나 밀접한지, 결과 하나를 독립적으로 맡길 수 있는지, 중간 판단과 장기 복구가 필요한지**가 더 중요하다.

## 한눈에 비교하기

| 구분 | 직접 작업 | Delegate | Run |
|---|---|---|---|
| 기본 형태 | HEAD가 이해부터 검증까지 이어서 처리 | 하나의 독립된 결과를 맡은 Agent가 한 번 반환 | 합의된 전체 계획을 여러 실행 결과와 점검 지점으로 진행 |
| 적합한 상황 | 실행과 판단이 현재 전체 맥락에 강하게 연결됨 | 다른 소유자가 한 번에 완성할 경계가 분명함 | 의존하는 결과가 여러 개이고 중간 판단이나 복구가 필요함 |
| 전체 목표의 소유자 | HEAD | HEAD | HEAD |
| 실행 결과의 소유자 | HEAD | 맡은 Agent | 각 단계의 실행 담당자 |
| 지속 기록 | 현재 Session의 맥락 | 위임 결과와 근거를 HEAD가 다시 통합 | 계획, 현재 위치와 점검 결정을 Run 기록으로 보존 |
| 완료 판단 | HEAD | Agent 반환을 확인한 HEAD | 실행과 분리된 점검 HEAD가 각 결과를 전체 Plan에서 검토 |

## 1. 직접 작업

직접 작업은 HEAD가 문제 이해, 실행, 수정과 검증을 하나의 연결된 흐름에서 처리하는 방식이다.

별도의 작업자에게 설명하고 다시 결과를 넘겨받는 것보다, HEAD가 이미 확보한 전체 맥락을 그대로 유지한 채 진행하는 편이 결과를 더 잘 보존할 때 사용한다.

### 언제 적합한가

- 조사와 수정, 검증이 서로 긴밀하게 이어져 있다.
- 작업을 떼어 내면 중요한 관계를 다시 설명해야 한다.
- 하나의 흐름 안에서 실제 결과까지 확인할 수 있다.
- 별도 점검 지점이나 장기 복구 구조가 필요하지 않다.

직접 작업은 반드시 작거나 간단한 작업만을 뜻하지 않는다. 여러 파일을 읽고 도구를 사용하거나 몇 차례 수정할 수도 있다. 핵심은 **HEAD의 현재 이해와 실행을 분리하는 것이 이득인지**다.

```text
HEAD가 목표와 근거를 이해
  → 직접 조사하고 실행
  → 실제 결과를 확인하고 수정
  → 전체 목표를 기준으로 완료 판단
```

## 2. Delegate

Delegate는 HEAD가 **독립적으로 완성할 수 있는 결과 하나**를 정한 뒤, 그 결과를 맡을 Agent에게 한 번 위임하는 방식이다.

예를 들어 경계가 명확한 코드 변경, 정해진 기준에 따른 검토, 하나의 완결된 자료 제작처럼 다른 소유자가 처음부터 끝까지 책임질 수 있는 결과가 여기에 해당할 수 있다.

### 위임하기 전에 HEAD가 정하는 것

- 왜 이 결과가 필요한가
- 정확히 무엇을 만들어야 하는가
- 누가 그 결과를 사용할 것인가
- 어떤 출처와 결정이 기준인가
- 무엇을 바꾸고 무엇을 보존해야 하는가
- 어떤 실제 근거로 결과를 확인할 것인가

Agent는 이 경계 안에서 필요한 로컬 조사와 실행 방법을 판단하고, 결과물과 직접 근거를 함께 반환한다. 반면 전체 프로젝트의 목표, 중요한 제품·정책 결정, 위임 결과를 받아들일지에 대한 판단은 HEAD에 남는다.

```text
HEAD가 전체 결과를 이해
  → 독립된 결과 하나와 경계를 정함
  → Agent가 구현·수정·검증 후 한 번 반환
  → HEAD가 실제 결과를 읽고 전체 목표에 통합
```

Agent의 “완료했다”는 보고만으로 작업이 끝나는 것은 아니다. 반환된 산출물과 근거는 HEAD의 최종 판단에 쓰이는 증거이며, 부모 작업의 새로운 기준이 되지는 않는다.

위임 도중 중요한 결정이 빠졌거나 정해진 경계로 결과를 만들 수 없다는 사실이 드러나면 Agent가 임의로 전체 방향을 바꾸지 않는다. 충돌을 HEAD에게 돌려보내고, HEAD가 직접 해결하거나 사용자 결정을 요청하거나 작업 방식을 다시 선택한다.

## 3. Run

Run은 사용자가 동의한 전체 설계를 **여러 개의 연결된 실행 결과로 안전하게 이어 가기 위한 지속 작업 방식**이다.

다음과 같은 경우에 사용한다.

- 앞 단계의 결과가 다음 단계의 입력이 된다.
- 서로 독립적인 몇 가지 결과를 만든 뒤 다시 통합해야 한다.
- 중간 결과를 전체 계획에 비추어 판단해야 한다.
- 대화 중단이나 컨텍스트 압축 이후에도 정확한 위치에서 복구해야 한다.
- 한 번의 위임으로는 전체 결과를 책임 있게 완성할 수 없다.

Run을 시작하기 전에는 사용자와 중요한 설계 및 방향이 합의되어 있어야 한다. 그 계획은 실행 중에도 전체 의미를 판단하는 기준으로 남는다.

### Run의 기본 단위

- **Accepted Plan Baseline**: Problem Definition, Goals/Evidence, 대안과 사용자 선택, Selected Solution, Result Graph를 보존하는 전체 기준
- **Result**: 다음 소비자가 독립적으로 사용할 수 있는 입력·출력·검증·보존 경계
- **Execution Contract**: Runner가 실행 전 Result 하나에 대해 고정하는 정확한 작업 계약
- **Checkpoint**: 저장된 Planner가 Produced Result와 Worker Report/Evidence를 Plan에 다시 연결해 판단하는 지점

```text
사용자가 전체 설계에 동의
  → Plan을 실행 기준으로 보존
   → 현재 안전하게 준비된 Result horizon을 선택
   → Runner가 각 Result의 Execution Contract를 작성하고 실행
   → 저장된 Planner Checkpoint에서 실제 결과를 Plan 기준으로 검토
  → 다음 결과를 선택하거나 수정·재결정
  → 전체 Plan의 실제 결과가 성립하면 종료
```

`run.json`은 `run.md`, 최신 Checkpoint, 현재 Execution Contract만 가리키는 포인터 파일이다. 복구는 이 포인터를 따른다. 저장된 Planner 검토에는 Plan 파일을 다시 전달하지 않는다. 기존 legacy Run은 자동 마이그레이션 없이 기존 복구 경로로 유지된다.

점검에서는 작업 보고나 테스트 결과만 보는 것이 아니다. 실제 산출물이나 상태에서 최소한의 대표 경로가 성립하고, Plan의 다음 소비자가 그 결과를 사용할 수 있는지 확인한다. 계획된 단계를 모두 수행했다고 자동으로 끝나는 것이 아니라, 점검이 전체 합의 결과와 대표 흐름의 성립을 확인했을 때 Run이 완료된다.

실행 중 전체 의미를 바꿔야 한다면 단순한 로컬 수정으로 처리하지 않는다. 계획 변경이 필요하다는 사실을 분리하고, 중요한 방향이라면 사용자와 다시 결정한 뒤 새로운 실행 기준을 세운다.

## 어떻게 선택하는가

HEAD는 다음 순서로 생각할 수 있다.

```text
현재 이해와 실행을 한 흐름으로 유지하는 것이 가장 좋은가?
  └─ 그렇다 → 직접 작업

결과 하나를 독립된 소유자에게 완전한 경계로 맡기고 한 번에 돌려받을 수 있는가?
  └─ 그렇다 → Delegate

합의된 전체 결과에 여러 의존 작업, 점검 지점 또는 장기 복구가 필요한가?
  └─ 그렇다 → Run
```

작업이 복잡하다는 이유만으로 Run을 만들거나, Agent가 있다는 이유만으로 위임하지 않는다. 반대로 처음에는 직접 시작했더라도 독립된 결과의 경계가 드러나면 Delegate를 선택할 수 있고, 여러 의존 결과와 점검 필요성이 확인되면 사용자와 계획을 합의한 뒤 Run으로 전환할 수 있다.

어느 구조가 필요한지 분명하지 않다면, HEAD가 전체 맥락을 유지하는 직접 작업에서 시작한다.

## 세 방식에서 변하지 않는 것

어떤 방식을 쓰더라도 다음 원칙은 같다.

- 사용자와 합의한 전체 결과가 기준이다.
- 중요한 방향과 외부 행동의 권한은 사용자에게 남는다.
- HEAD는 전체 맥락과 통합 판단을 계속 소유한다.
- Agent나 실행 담당자는 맡은 경계 안의 결과와 로컬 방법을 소유한다.
- 보고서, 계획, 테스트는 근거이지만 실제 작동 결과를 대신하지 않는다.
- 가능한 경우 입력부터 실제 소비자까지 이어지는 대표 흐름으로 완료를 확인한다.
