# 개발

필요한 것만 읽기 쉬운 구조로 만들고, 실제로 실행해 본 증거를 확인해 마무리한다. 아래 기준은 계획하는 쪽, 구현하는 쪽, 검수하는 쪽이 함께 쓴다. 저장소 구조·도구·명령 같은 프로젝트 관례는 프로젝트 문서를 따르고, 설계·구현·검증·검수는 이 스킬의 기준을 따른다. 구현이나 검수를 맡길 때는 맡는 에이전트도 이 스킬을 읽게 하고, 스킬을 읽을 수 없는 환경이면 필요한 절을 브리프에 넣어 준다.

## 1. 필요한 것만 만든다

**배경**
코드를 추가하면 그만큼 읽고 관리하고 나중에 함께 고쳐야 할 부분이 늘어난다. 당장 쓰지 않는 옵션이나 확장 구조를 미리 만들어 두면 관리할 부담만 늘어난다. 기존 코드의 방식도 그때의 사정에 맞춰 짠 것일 수 있으므로, 기존 코드에 있다는 이유만으로 그대로 따라 하지 않는다.

**지침**
- 범위는 요청된 동작과, 변경 뒤에도 지켜야 할 기존 동작으로 정한다.
- 관련된 기존 구현을 먼저 읽고, 이미 같은 일을 하는 코드가 있으면 그것을 쓴다.
- 기존 관례가 요구와 이 스킬의 기준에 맞으면 따른다. 크게 어긋나면 그 차이를 계획하는 쪽에 알리고 정해진 대로 한다.
- 무언가를 추가할 때는 그것이 없으면 무엇이 안 되는지 말할 수 있어야 한다. 관련 없는 개선은 이번 변경에 넣지 않고 따로 알린다.

**범위**: 모든 코드 변경에 쓴다. 정리·리팩터링을 요청받았으면 그 정리가 요청된 동작이다.

## 2. 업무 규칙과 검사는 한곳에서만 처리한다

**배경**
같은 규칙이나 검사를 여러 곳에서 따로 구현하면, 시간이 지나며 서로 다르게 동작하고, 수정할 때 한 곳을 놓치기 쉽다. 여러 책임이 한 모듈에 섞여 있으면 하나를 고칠 때 나머지까지 이해해야 한다.

**지침**
- 업무 규칙과 입력·권한·상태 검사는 그 일을 책임지는 한 곳에서 처리한다. 앞 단계에서 이미 검증한 조건은 그 결과를 쓴다. 다만 신뢰 경계가 달라지거나(예: 클라이언트에서 서버로) 그사이 상태가 바뀌었으면 다시 검사한다.
- 각 모듈은 입력·출력·상태 변화만 알면 쓸 수 있게 만든다. 전체 처리 순서는 흐름을 담당하는 코드에서 한눈에 보이게 한다.
- 새 계층이나 추상화는 책임이나 의존 관계가 분명해질 때만 추가한다.
- 오류가 나면 이미 정해진 오류 처리 경로로 넘긴다. 재시도나 대체 동작은 요구된 실패 처리에 필요할 때만 넣는다.

**범위**: 모듈·함수·업무 규칙·검사를 추가하거나 바꾸거나 옮길 때 쓴다. 업무 규칙을 건드리지 않고 한 모듈 안에서만 바뀌는 수정에는 쓰지 않는다.

## 3. 같은 데이터는 한 곳에만 저장한다

**배경**
데이터는 한번 쌓이면 코드보다 오래 남고 고치기도 어렵다. 같은 데이터가 두 군데에 저장되거나 여러 코드가 제각각 수정하면, 언젠가 두 값이 달라지고 어느 쪽이 맞는지 알 수 없게 된다.

**지침**
- 새 테이블이나 칼럼을 만들기 전에, 같은 데이터가 이미 저장돼 있는지 확인한다. 이미 있으면 그것을 쓴다.
- 한 데이터의 값을 바꾸는 책임은 한 곳(모듈이나 서비스)에 둔다.
- 다른 데이터로 계산할 수 있는 값(합계, 개수, 상태 요약 등)은 필요할 때 계산한다. 속도 때문에 따로 저장해야 하면, 그 이유와 원래 데이터가 바뀔 때 함께 갱신하는 위치를 기록한다. 이력처럼 그 시점의 값을 남기는 데이터는 원래 데이터가 바뀌어도 그대로 둔다.
- 의미가 다른 데이터는 칼럼을 나눠 저장한다.
- 데이터를 언제 삭제하는지(탈퇴, 만료 등)를 처음에 정한다.

**범위**: 테이블·칼럼·저장 파일·캐시를 추가하거나 바꿀 때 쓴다. 저장 구조를 건드리지 않는 변경에는 쓰지 않는다.

## 4. 결정과 미룬 이유는 주석이 아니라 정본에 남긴다

**배경**
에이전트는 코드 바로 옆의 주석을 가장 가까운 지시로 읽는다. "임시로 이렇게 둔다", "나중에 고친다" 같은 주석이 있으면 임시방편이 괜찮은 방식처럼 보여, 다음에 작업하는 쪽도 그대로 따라 하게 된다. 반면 외부 API의 호출 제한이나 라이브러리 버그 같은 외부 제약은 코드만 봐서는 알 수 없으므로 해당 코드 옆에 주석으로 남겨야 한다.

**지침**
- 우리가 내린 결정은 기획서·정책·결정 기록에, 미룬 일은 할 일 목록에 남긴다. 임시방편으로 처리한 곳은 근본 원인을 고치는 일을 할 일 목록에 따로 남긴다. 이런 문서가 없는 프로젝트에서는 커밋 메시지와 작업 기록에 남긴다.
- 정본에는 관련 코드 위치를, 커밋 메시지에는 정본의 위치를 적어 서로 찾아갈 수 있게 한다.
- 외부 제약은 해당 코드 옆에 주석으로 짧게 적고 출처(이슈·문서 주소)를 단다.
- 우리 코드 안에서 지켜야 하는 기술 조건(예: 이 함수는 락을 잡은 뒤 부른다)은 먼저 타입·검사·이름으로 코드에 드러낸다. 그렇게 할 수 없을 때만 그 조건을 짧은 주석으로 적고, 이유나 미룬 사정은 적지 않는다.
- 기존 주석을 믿기 전에 실제 동작 및 정본 문서와 맞는지 대조해 본다. 주석과 실제 동작이 다르면 실제 동작을 기준으로 삼는다. 실제 동작과 정본이 다르면 버그인지 정본이 바뀐 것인지 계획하는 쪽이 확인한다.

**범위**: 코드를 쓰거나 고칠 때, 코드가 왜 그런지 찾을 때 쓴다. 언어·도구가 쓰는 주석(API 문서 주석, 타입 주석, 린트 지시, 라이선스 머리말)에는 쓰지 않는다.

## 5. 되풀이되는 실수는 자동 검사나 구조로 막는다

**배경**
문서로 적어 둔 지침은 놓치기 쉽고 지켰는지 일일이 확인하기도 어렵다. 린트·타입·테스트 같은 자동 검사나 실수하기 어려운 코드 구조로 만들어 두면 누가 코드를 짜든 같은 실수를 매번 막을 수 있다.

**지침**
- 같은 종류의 실수를 이미 고친 적이 있다는 것을 알게 되면(작업 기록, 검수 지적, 사용자의 말에서), 지침을 한 줄 더하기 전에 자동 검사나 구조로 막을 수 있는지 본다.
- 막을 수 있으면 지금 작업에 섞지 않고 별도 작업으로 등록한다. 구현하는 쪽이 발견했으면 계획하는 쪽에 알린다.
- 검사의 오류 메시지에는 무엇이 문제이고 근본 원인을 어떻게 고치는지 적는다.
- 새로 생기는 것부터 막고, 이미 있는 것은 그다음에 정리한다.

**범위**: 앱 코드에서 같은 종류의 실수가 되풀이될 때 쓴다. 한 번뿐인 실수나 상황마다 판단이 필요한 설계 선택에는 쓰지 않는다.

## 6. 실제 환경에서 써 보고 증거로 완료를 확인한다

**배경**
코드를 눈으로 읽거나 테스트가 통과했다는 보고만으로는 실제로 잘 동작하는지 확신할 수 없다. 실제 입력을 넣어 최종 결과가 쓰이는 곳까지 직접 실행해 봐야 동작을 확인할 수 있다. 화면·출력 같은 증거가 있으면 받는 쪽은 코드를 다시 읽지 않고 증거로 판단할 수 있다.

**지침**
- 작업 전에 실행해 볼 경로와 확인할 항목, 테스트 범위를 정한다. 개발 방향을 쓰는 작업이면 거기에 함께 적고, 개발 방향 없이 하는 작은 수정이면 코드를 고치기 전에 작업 기록에 적는다.
- 완료할 때 그 경로를 실제 환경(실제 서비스와 같은 구성의 개발 서버 등)에서 사용자가 쓰듯 실행한다.
- 항목마다 통과·실패·확인 못함 중 하나와 증거(화면, 출력, 기록)를 남긴다. 확인하지 못한 항목은 이유와 함께 보고하고, 그대로 완료 처리할지는 결과를 받는 쪽이 정한다. 제품 동작이나 합의한 결과에 영향을 주는 문제면 사용자가 정한다.
- 테스트는 바뀐 동작, 관련된 회귀, 중요한 불변 조건을 지키도록 고른다. 테스트 개수나 커버리지는 목표가 아니며, 이미 확인되는 동작이면 새 테스트를 더하지 않는 것도 정당한 결정이다.
- 구현하는 쪽은 정해진 테스트 범위대로 하고, 부족하다고 보면 그 사실을 계획하는 쪽에 알린다.
- 받는 쪽은 보고 문장이 아니라 증거를 직접 본다.

**범위**: 실행되는 코드를 바꾼 작업(동작을 지켜야 하는 리팩터링 포함)을 끝낼 때, 맡긴 개발을 받을 때 쓴다. 문서·주석만 바꾸는 일에는 쓰지 않는다.

## 7. 개발 방향에는 미리 합의할 것만 정한다

**배경**
데이터의 의미, 외부 계약, 권한, 과금, 외부 의존은 나중에 바꾸기 어렵고 제품 동작에 직접 영향을 주므로 구현 전에 합의해야 한다. 반면 함수 분리, 이름, 내부 알고리즘은 코드를 보며 구현하는 쪽이 가장 잘 정한다. 계획하는 쪽이 그것까지 미리 정하면 구현하는 쪽이 실제 코드와 맞지 않는 계획을 따르게 된다.

**지침**
- 개발 방향은 그 일의 작업 기록에 쓴다. 담을 것: 구현할 동작과 제외할 범위(1절), 재사용할 코드와 새 동작을 맡을 모듈·주요 연결, 바뀌는 데이터·계약·의존과 그 이유, 실행해 볼 경로·확인 항목·테스트 범위(6절), 사용자가 정할 것.
- 데이터 의미·외부 계약·주요 책임 경계·권한·과금·주요 외부 의존을 바꾸는 것은 구현 전에 이유를 밝혀 사용자와 합의한다. 새로 저장할 데이터를 추가할 때는 왜 필요한지 개발 방향에 밝힌다. HEAD가 직접 구현할 때도 같다.
- 오류가 나거나 동시에 실행될 때 금액·데이터 무결성·권한에 문제가 생길 수 있으면, 실행 순서와 한 묶음으로 처리할 범위(모두 성공하거나 모두 실패해야 하는 범위)를 적는다.
- 합의된 범위 안의 함수 분리·이름·내부 알고리즘은 구현하는 쪽에 맡긴다. 구현하는 도중에 새로 합의할 사항이 나오면 구현하는 쪽은 계획하는 쪽에 알리고, 계획하는 쪽이 개발 방향을 고친 뒤 구현을 이어 가게 한다.
- 작은 변경은 짧게 쓰고, 대안과 위험은 실제로 검토할 것이 있을 때만 적는다.

**범위**: 기획이 합의된 뒤 구현을 시작하거나 맡기기 전에 쓴다. 합의할 것이 없는 작은 수정은 개발 방향 없이 고치고, 6절의 실행해 볼 경로·확인 항목·테스트 범위만 먼저 적는다.

## 8. 검수는 같은 기준으로 한다

**배경**
계획·구현 때와 다른 기준으로 검수하면 꼭 고쳐야 할 문제와 개인 취향이 뒤섞인다. 같은 기준으로 검수해야 빠뜨린 것과 불필요하게 더 만든 것을 정확히 짚을 수 있다.

**지침**
- 검수자 자신이 생각하는 이상적인 설계가 아니라 위 1~7절을 기준으로 본다. 기존 동작에 대한 주장은 실제 코드와 합의된 요구에 맞춰 본다.
- 코드 변경이면 확인 항목마다 실제 환경의 증거가 있는지, 개발 방향이면 실행해 볼 경로·확인 항목·테스트 범위가 적혀 있는지 본다.
- 작업 기록이나 이전 검수 결과에서 같은 지적을 찾으면, 자동 검사로 막을 일로 함께 적는다(5절).
- 찾은 만큼만 적는다. 지적이 없는 검수도 정상 결과다.

**범위**: 코드 변경과 개발 방향을 검수할 때 쓴다. 기획서·화면 시안 검수에는 각자의 기준을 쓴다.
