# 제품 그래프

## 1. 제품 그래프는 왜 필요한가

LLM은 코드 한 조각은 잘 읽지만, 제품 전체를 엮어 볼 맥락이 없고 유저가 무엇을 겪는지 모른다. 그래서 이미 있는 기능을 새로 만들고, 정해 둔 정책과 다르게 고치고, 한 곳을 바꿀 때 함께 바뀌어야 할 곳을 놓친다. 제품 그래프는 이런 문제를 막기 위해 쓴다.

- **사람의 말에서 관련 코드 위치를 찾는다**: "무료 유저가 넷째 메시지를 보내면 이상하다" 같은 말을 유저 활동 → 화면요소 → 기능 → 코드 → DB 순서로 따라가 실제 코드 위치를 찾는다.
- **원래 정한 정책을 확인하게 해 준다**: 코드만 봐서는 지금 동작이 의도한 것인지 알 수 없지만, 그래프에서는 연결된 정책을 함께 확인할 수 있다.
- **바꾸면 영향받는 곳을 보여 준다**: 연결을 따라가 함께 바뀔 화면·기능·정책·데이터를 모은다.
- **전체 구조를 먼저 보여 준다**: 어떤 기능이 어디에 있는지 한눈에 보여 주어, 이미 있는 기능을 중복해서 만들지 않게 한다.

## 2. 기획 흐름이 곧 그래프다

제품 그래프는 새로 만든 개념이 아니다. 기획은 원래 제품 정의서 → 유저 저니맵 → 유저플로우 기획서(유저 활동) → IA·화면설계서(화면과 화면요소) → 정책 → 기능 → 개발(코드·DB) 순서로 이어진다. 각 단계의 문서는 앞 단계의 어느 항목을 바탕으로 나왔는지 분명하게 이어져 있고, 이 관계가 원래부터 있는 연결 고리다. 제품 그래프는 이 고리를 문서와 코드에서 뽑아 이어 붙이고 DB에 넣어, 한 번에 조회할 수 있게 한 것일 뿐이다.

그래서 그래프는 기획 문서를 읽던 방식 그대로 위에서 아래로 읽는다. 그래프에서 실제로 따라가는 연결은 유저 활동 → 화면요소 → 기능 → 코드 → DB다. 화면은 화면요소를 담고, 정책은 화면과 기능에 걸린다. 제품 정의서·유저 저니맵·IA는 연결로 잇지 않고, 아래 내용이 거기에 맞는지 맞춰 본다.

앞 단계와 뒤 단계가 어긋나면 뒤 단계가 잘못 만들어졌거나, 그사이에 기획이 바뀐 것이다. 앞 단계 문서를 코드에서 거꾸로 추정해 쓴 경우라면 그 추정이 틀렸을 수도 있다. 어느 쪽인지는 제품 주인이 판단한다.

## 3. 제품 그래프란

제품 그래프는 특정 시점의 제품 구조를 노드와 연결 관계로 정리한 지도다.

- **제품 쪽 노드**: 제품코어, 유저저니, 유저 활동, IA(화면이 이어지는 구조), 화면, 화면요소(화면에서 유저가 보거나 누르거나 입력하는 것), 정책(조건·주체·행위의 규칙), 기능(시스템이 하는 일 하나. 대개 API 하나 크기이고, 기획에서 흔히 말하는 '기능'은 유저 활동에 가깝다)
- **코드 쪽 노드**: 코드(파일·함수와 그 묶음), DB(테이블·칼럼), 데이터, 외부 연결, 계측 이벤트
- 노드는 기획 문서와 코드에서 뽑아 만든다. 그래프에 직접 쓰는 것은 정책의 규칙 한 줄과, 기능·DB·이벤트의 뜻 한 줄 정도다.
- 알림·메일·외부 결제창처럼 제품 화면 밖에서 유저가 겪는 것과, 제품을 바꿔 온 흐름(지표, 가설, 계획, 배포)은 제품 그래프에 넣지 않는다.

조회 명령은 그 프로젝트의 그래프 안내를 따른다. 그래프를 만들고 갱신하는 법은 이 스킬에서 다루지 않는다.

## 4. 그래프로 시작하고 원본으로 확인한다

**배경**
파일을 직접 훑어서 찾으면 미처 발견하지 못한 관련 코드나 정책이 있는지 알기 어렵다. 그래프는 한 번 조회로 관련된 것을 넓게 모으고, 이미 정한 정책과 영향받는 곳을 함께 보여 준다. 다만 그래프는 마지막으로 갱신한 시점의 지도이고, 제품의 모든 것을 담고 있지는 않다. 그래서 그래프로 어디를 볼지 정하고, 지금의 사실은 원본에서 확인한다.

**지침**
- 기획을 시작하거나 앱 내부를 조사할 때는 해당 부분의 현재 동작 흐름, 기존 정책, 관련 코드·데이터를 그래프에서 먼저 확인한다.
- 그래프로 읽을 원본(코드·문서·데이터)을 좁힌 뒤, 그 원본을 직접 읽어 확인한다. 읽고 근거를 다는 법은 조사 스킬을 따른다. 그래프에서 찾지 못한 부분은 원본을 직접 조사하고, 그래프에 없었다는 것을 함께 적는다.
- 그래프의 코드·데이터 정보가 실제 원본과 다르면 그래프가 아직 갱신되지 않은 것이므로 원본을 기준으로 삼는다.
- 그래프의 정책이나 기획 문서 내용이 실제 코드의 동작과 다르면 버그인지 기획이 바뀐 것인지 단정할 수 없다. 그 차이가 지금 내릴 판단에 영향을 주면 사용자에게 확인한다.
- 기록하거나 보고할 때는 원본으로 확인한 부분과 그래프로만 본 부분을 나눠 적는다. 찾은 차이는 지금 일의 작업 기록에 적는다.

**범위**: 제품 그래프가 있는 앱의 기획, 내부 구조·코드·정책 조사, 지금 동작이 의도한 것인지 판단할 때 쓴다. 그래프가 없는 앱은 조사 스킬대로 원본을 직접 조사한다. 그래프를 만들거나 갱신하는 일에는 쓰지 않는다.
