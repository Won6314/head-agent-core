# Start Job

일은 네 장의 글로 내려간다. 앞 장이 정해져야 다음 장을 쓴다. 코드는 넷째 장이 끝난 뒤에만 쓴다.

| 장 | 무엇 | 누가 보는가 |
|---|---|---|
| 1. 문제·목표·조건 | 무엇이 안 되고, 무엇을 원하고, 무엇은 건드리면 안 되는가 | 사용자와 맞춘다 |
| 2. 사용 흐름 | 사용자가 무엇을 하면 무엇이 보이고 무엇이 바뀌는가, 한 문단 | 사용자가 승인한다 |
| 3. 구현 설계 | 어떤 구성요소가 생기거나 바뀌고, 각각 무엇을 맡고, 어떻게 이어지는가 | LLM이 쓰고 파일로 남긴다 |
| 4. 구현 | 코드 | — |

코드가 아닌 질문, 사용자가 무엇을 어떻게 바꿀지 이미 말한 작은 수정에는 이 스킬을 쓰지 않는다.

## 1. 문제·목표·조건을 맞춘다

- 사용자의 말과 대화, 이미 있는 자료를 읽고 문제·목표·조건을 각각 한두 줄로 쓴다.
- 사용자가 한 말과 내가 덧붙인 것을 구분해서 보인다. 덧붙인 것은 "제가 덧붙인 것:"으로 따로 적는다.
- 무엇을 만들지가 아직 정해지지 않았으면 2장으로 가지 않고 그것부터 묻는다.
- 사용자가 맞다고 하면 기록한다(`session_save`). 이 대화에 작업 주제가 없으면 이때 맞춘다.

## 2. 사용 흐름으로 "이렇게 할까요"를 묻는다

- 시작부터 사용자가 보는 결과까지를 한 문단으로 쓴다. 사용자가 쓰는 말로 쓰고, 코드·파일·라이브러리 이름은 쓰지 않는다.
- 1장의 목표와 조건에서 나오는 것만 쓴다. 1장에 없는 기능은 넣지 않는다.
- 사용자가 승인하면 3장으로 간다.

## 3. 구현 설계를 쓴다

- 높이: C4 모델의 Component 수준(Code 수준 아님)이다. 개발 회의에서 화이트보드 앞에 서서 동료 개발자에게 "이렇게 만들 거야"라고 설명하듯 쓴다.
- 적는 것: 새로 생기거나 바뀌는 구성요소, 각각이 맡는 일, 서로 어떻게 이어지는지, 동작을 바꾸는 결정(어디에 저장하는지, 무엇을 어디서 판정하는지, 어떤 기술을 쓰는지).
- 적지 않는 것: 이미 쓰고 있는 스택과 라이브러리 소개, 함수 시그니처, 데이터 구조의 필드 목록, 코드.
- 1·2장에 없는 기능과 처리(중복 실행 방지, 재시도, 로그, 백업 같은 것)는 넣지 않는다. 꼭 필요해 보이면 본문 밖 "물어볼 것"에 한 줄로 적는다.
- 2장만으로 정해지지 않고 사용 흐름이 돌려면 꼭 정해야 하는 것은 사용자에게 묻는다. 그 밖의 경우는 묻지도 넣지도 않는다.
- 다 쓰면 파일로 남기고(예: `.head/plans/<이름>.md`), 사용자에게는 "구현 설계를 이 파일에 남겼어요"와 물어볼 것만 말한다.

예: "클립보드 기록을 트레이에서 다시 붙여넣기" 앱의 구현 설계 일부

> 트레이 상주 앱 하나로 만든다(.NET WinForms). 클립보드 감시는 Windows 클립보드 변경 알림을 받는 숨은 창이 맡고, 새 텍스트가 오면 기록 저장소에 넘긴다. 기록 저장소는 최근 50개를 메모리에 들고 바뀔 때마다 AppData의 파일 하나에 통째로 쓴다. 트레이 메뉴는 열릴 때 저장소에서 목록을 받아 그리고, 항목을 고르면 클립보드에 다시 넣는다. 같은 텍스트가 연달아 오면 하나로 친다는 판정은 저장소 한 곳에서만 한다.

## 4. 구현한다

- 3장에 적힌 것만 만든다.
- 구현하다 3장에서 끌어낼 수 없는 결정을 만나면 덧붙이지 않고 멈추고, 3장을 고칠지 사용자에게 묻는다.

## 끝나면 보고한다

사용자에게는 2장의 말로 네 가지를 보고한다: 된 것, 계획과 달라진 것과 그 이유, 계획에 없이 더한 것, 하지 않았거나 확인하지 못한 것. 그리고 기록한다(`session_save`).
