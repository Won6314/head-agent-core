# head-context 0.9.5 제품 그래프 — LLM용 조회 안내

이 그래프는 head-context 플러그인(head-agent-core commit `04e9328`, `packages/context`)을 노드와 연결로 기록한 인덱스다. 물음을 받으면 그래프로 볼 곳을 좁히고, 그래프가 가리킨 원문을 읽은 뒤 답한다.

## 시작

이 파일이 있는 폴더에서 실행한다. Python 3 표준 라이브러리만 쓰고, 읽기만 한다.

```
python3 hc_graph.py overview
```

노드 종류별 수, 유저가 받는 글의 묶음, 유저 활동 목록, 기능 목록이 나온다. 처음 한 번 보고 물음에 맞는 명령으로 내려간다.

## 노드 종류

이 플러그인에는 그림으로 된 화면이 없다. 그래서 "화면"은 유저가 받는 출력 한 종류를 뜻한다. 유저는 사람이거나 그 사람이 쓰는 AI agent다.

| 종류 | 이 그래프에서 무엇인가 | ID 예 |
|---|---|---|
| 제품코어 | 이 플러그인이 무엇이고 누구를 위한 것인가 | `product:head-context` |
| 유저 활동 | 유저가 한 가지 일로 받아들이는 활동과 그 차례 | `ua.record` |
| 화면 | 유저가 받는 출력 한 종류(tool 결과, hook이 넣는 글, 오류 메시지 등) | `TOL-03` |
| 화면요소 | 그 출력 안의 한 부분 | `TOL-03#1` |
| 기능 | 앱이 부르는 입구 하나: MCP tool, hook, CLI 명령, MCP 요청, skill | `tool:save`, `hook:claude:SessionStart:recent` |
| 정책 | 조건 / 주체 / 행위로 쓴 규칙 하나 | `pol.close-needs-recap` |
| 코드 | 파일·함수·메서드 등 이름 있는 코드 | `code:core/sessions.mjs#sessions.save` |
| 데이터 | 코드가 읽고 쓰는 파일·환경 변수 | `data:env:HEAD_CONTEXT_PERSON` |
| DB | 플러그인이 쓰는 SQLite 색인의 테이블과 컬럼 | `db:nodes.id` |
| 외부 연결 | 코드가 플러그인 밖을 부르는 곳(소켓, 프로세스 표 등) | `ext:Claude 수신함 소켓` |

## 물음에 맞는 명령

| 물음 | 명령 |
|---|---|
| 이 기능을 고치려면 어디를 보나 | `feature tool:save` — 처리 코드에서 call·callback·framework-invoked로 닿는 코드 트리, 줄마다 읽고 쓰는 것 |
| 이 코드를 바꾸면 무엇이 걸리나 | `impact sessions.closeBranch` — 그 코드에 닿는 기능과 그 기능의 화면·정책 |
| 유저가 이 일을 할 때 무엇이 어떻게 도나 | `user ua.resume` — 유저 활동 → 화면요소 → 기능 → 처리 코드 → 데이터 |
| 이 출력은 무엇이고 어느 기능이 내나 | `screen STA-04` |
| 이 동작은 정해 둔 규칙인가 | `policy <정책 ID>`, 또는 `find <낱말> --type 정책` |
| 이름만 알 때 | `find 압축` (`--type 화면요소`처럼 좁힐 수 있다) |
| 노드 하나의 속성과 연결 전부 | `show TOL-03#1` |
| 원문 읽기 | `source <ID>` — 문서 노드는 원문 글, 코드 노드는 파일·줄. `--repo <head-agent-core>/packages/context`를 주면 그 줄을 보인다 |
| 직접 SQL | `schema`로 테이블 꼴을 보고 `sql "SELECT …"` (읽기 전용) |

코드 노드는 ID, `code:`를 뗀 꼴, 함수 이름, 한정 이름 어느 것으로 줘도 된다. 이름이 겹치면 후보를 보이고 멈춘다. `--json`을 붙이면 JSON으로 나온다.

## 답하는 법

1. 그래프로 관련 노드와 파일·줄을 찾는다.
2. 그 원문을 읽는다. 코드는 `git -C <head-agent-core> show 04e9328:packages/context/<파일>`로 읽는다. 작업 트리가 다른 판이면 줄 번호가 어긋난다.
3. 원문을 읽은 뒤에 답한다. 그래프는 찾아가는 지도이고, 지금 동작을 정하는 것은 원문이다.
4. 그래프에서 아무것도 나오지 않아도 그것이 없다는 뜻은 아니다. 원문을 직접 찾는다.

## 연결의 근거

- 코드끼리의 연결은 스크립트가 구문 트리와 TypeScript 타입 검사기로 뽑았다. 따라가는 종류는 call(부름), callback(함수를 값으로 넘김), framework-invoked(경로로 실행)다.
- 화면요소 ↔ 기능 연결은 두 근거뿐이다. `실행 R번호`는 플러그인을 실제로 돌린 출력에서 그 글이 나온 것이고, `코드 파일:줄`은 그 글을 만드는 코드 자리다. 연결의 `근거` 속성에 적혀 있다.
- 유저 활동의 `실제와 다름` 줄은 정해 둔 규칙을 시험 한 번에서 agent가 어긴 사실이다. 경향이 아니다. `관찰` 줄은 규칙 위반이 아닌 사실이다.

## 한계

- `impact`에 나오는 화면요소는 그 기능이 내는 출력 후보 전부다. 그 코드를 바꿀 때 실제로 바뀌는 글은 코드 가지를 읽어 정한다.
- 플러그인이 따로 띄우는 스크립트 안으로는 따라가지 않는다. 그 자리에서 "경계에서 멈춤"을 보인다.
- 값을 읽기만 하는 참조(상수 읽기 등)는 잇지 않았다. 상수를 바꿨을 때의 영향은 `find`나 원문 검색으로 찾는다.
- 유저 활동은 Claude Code로 실제로 써 보고 썼다. Codex와 OpenCode 쪽은 코드만 보고 썼다.
