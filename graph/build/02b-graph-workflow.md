# 제품 그래프 실행지침

무엇을 담는지는 [그래프 정의](02a-graph-definitions.md)에 있다. 이 문서는 그래프를 만드는 순서다. 단계마다 어느 컨텍스트가 하는지, 그 컨텍스트의 입력과 결과물을 적는다.

## 컨텍스트

| 시선 | 이 컨텍스트가 하는 것 |
|---|---|
| 테스터 | 코드를 모른 채 화면의 상호작용 요소를 하나씩 전부 누르고, 계정 상태를 바꿔 가며 화면과 상태를 빠짐없이 찾는다 |
| 화면 기획자 | 화면 하나의 한 상태를 받아, 보이는 화면요소를 번호 붙여 화면 문구 그대로 적는다 |
| 처음 온 유저 | 아무 컨텍스트도 들지 않고 보이는 그대로 서비스를 이용한다 |
| 제품 기획자 | 앞 단계 결과를 받아 유저가 왜 오고, 무엇을 하고, 무엇을 얻는지를 기획 문서로 쓴다 |
| 코드 | 코드와 코드 그래프만 보고, 화면은 보지 않는다 |
| 통합 | 앞 단계 결과를 모두 받아 하나로 쓴다. A·B를 만든 컨텍스트와 다른 컨텍스트다 |

## 전체 차례

```
0. 준비
A. 화면에서 쓰기 → 임시 그래프 A (화면, 화면요소, 화면 정책, 조작 기록)
B. 코드에서 쌓기 → 임시 그래프 B (코드, 데이터, 외부 연결, DB, 계측 이벤트, 기능)
C. 기획안      → 임시 그래프 C (제품코어, 유저저니, IA, 유저 활동, 화면, 정책)
D. 셋을 합치고 실제 제품과 대조
```

A와 B는 서로의 결과를 입력으로 쓰지 않는다. 각 단계 끝에 그 층을 임시 그래프로 적재한다.

## 0. 준비

HEAD가 정한다.

- 대상: 웹 서비스 주소, 코드 커밋 하나.
- 화면이 없는 제품이면: 설치하고 실행하는 법.
- 실행 환경: 개발 서버. 실행 중인 코드가 기준 커밋과 다르면 차이를 적는다.
- 계정 상태 만드는 법: 게스트, 새 가입, 로그인 무료, 유료, 한도 소진, 관리자.
- 기존 자료: 기획안, 정책. C에서 기준으로 쓸 것과 대조만 할 것을 나눈다.
- 처음 하는 제품이면 화면 몇 장과 유저 활동 하나로 A~D를 먼저 한 번 끝까지 한다.

## A. 화면에서 쓰기

개발 서버의 실제 서비스를 실제 브라우저로 쓴다. 실제 데이터와 실제 응답으로 찍는다. 컨텍스트를 동시에 돌리면 컨텍스트마다 계정을 따로 둔다.

**화면이 없는 제품.** 브라우저 대신 제품을 설치해 실제로 실행한다. A-1은 명령·tool·hook을 하나씩 전부 실행하고, 상태를 바꿔 가며 받는 출력을 모은다. 조작 기록에는 실행한 것과 받은 출력 원문을 남긴다. A-2는 그림 대신 출력 원문을 남긴다.

**A-1. 탐색.** 테스터 시선의 컨텍스트가 한다.
- 입력: 서비스 주소, 계정 상태 만드는 법.
- 결과물:
  - 화면 × 상태 목록: 화면마다 있는 상태와 거기 가는 법.
  - 조작 기록: 조작마다 누른 것(화면, 상태, 요소), 나간 요청(메서드, 주소, 상태 코드, 순서), 스트림 이벤트, 바뀐 상태. 요청은 도구가 기록한다.

**A-2. 화면설계서와 그림.** 화면 기획자 시선의 컨텍스트가 한다.
- 입력: A-1의 화면 × 상태 목록.
- 결과물: 상태마다
  - 화면설계서(정의서의 화면 절 형식)
  - 원본 HTML·PNG
  - 위치 매칭본 HTML·PNG(화면요소마다 번호 상자, 번호 = 화면설계서 번호). 번호 상자가 화면요소 전체를 감싸야 한다.
- 조작 기록의 요청을 그 화면요소 → 기능의 근거로 붙인다.

**A-3. 유저처럼 써 보기.** 처음 온 유저 시선의 컨텍스트가 한다. 유저 활동 하나에 컨텍스트 하나.
- 입력: 시작 상황, 원하는 것, 계정 상태. 시작 상황은 HEAD가 A-1·A-2를 보고 정한다.
- 입력에서 제외: A-1·A-2의 결과.
- 결과물: 무엇을 하려 했나, 무엇을 알아들었나, 어디서 막혔나, 무엇을 얻었나, A-1 목록에 없던 길.

**A-4. 추정 문서.** 제품 기획자 시선의 컨텍스트가 한다.
- 입력: A-1~A-3의 결과 전부.
- 결과물: 유저 활동, 유저저니, IA, 제품코어. 화면만 보고 쓴 추정이라고 표시한다.

**A-5. 적재.** A-1~A-4를 임시 그래프 A에 넣는다. 요청은 메서드·주소 그대로 둔다(D에서 기능 ID와 매칭에 쓰는 값).

## B. 코드에서 쌓기

코드 시선의 컨텍스트가 한다. 뽑는 것은 스크립트로 하고, 같은 커밋이면 두 번 돌려 결과가 같아야 한다.

**B-1. 호출 방식 표.** 이 제품 코드가 함수를 부르고, DB에 접근하고, 외부를 부르고, 데이터를 읽고 쓰고, 이벤트를 보내는 방식을 전부 찾는다.
1. 후보 목록: 이 스택에서 가능한 방식(파일 이름 라우트, 정해진 메서드 이름, 데코레이터, 설정 파일 등록, 오류 필터).
2. 실제 목록: 코드에서 함수가 언급되는 모든 자리를 모양별로 나눈다(직접 호출, 데코레이터 인자, 등록 목록, 값으로 넘김, 문자열 이름, 인터페이스 구현). 아무도 import하지 않는 파일과 동적 실행(`eval`, 변수 `import`)도 모은다.
3. 이 제품의 표: 후보 중 실제로 쓰인 것 + 후보에 없는데 코드에서 나온 것.

**B-2. 처리 정하기.** 표의 방식마다 따라간다 / 경계로 둔다 / 범위 밖(테스트·개발용) 중 하나를 정한다. LLM 판단이라고 표시한다.

**B-3. 코드 그래프 뽑기.** 방식마다 스캔 스크립트를 짜서 코드, 코드 → 코드 연결과 종류, 서비스 사이 요청, 데이터, 외부 연결, DB, 계측 이벤트를 뽑는다. 코드를 C4로 묶는다. 묶는 규칙은 스택마다 한 번 정하고 판단이라고 표시한다.

**B-4. 기능 만들기.** 정의서의 기능 정의대로 스크립트로 만든다.
- 서버 쪽 입구마다 기능 하나. 기능 → 그 입구의 처리 코드.
- 다른 API를 호출만 하는 서버 액션·web 라우트는 그 API 기능의 처리 코드.
- 프론트 조작의 코드에서 call·framework-invoked·callback만 따라가 호출하는 API를 찾는다. render로 들어간 부품 안의 핸들러는 따라가지 않는다. 호출하는 API가 있으면 그 API 기능 → 이 조작의 코드. 없으면 이 조작이 프론트 기능.
- 화면 → 그 화면을 그리는 코드. 그 코드에서 call·framework-invoked·callback으로 호출하는 기능이 화면 → 기능.

**B-5. 검사.** 목록으로 만든다.
- 어느 기능의 처리 코드에서도 도달하지 않는 코드
- 프론트 코드가 없는 API 기능(웹훅, 서버끼리만 부르는 API 제외)
- 무작위 표본(씨앗 값 기록): 고른 기능의 코드를 원본과 대조한 맞음·틀림과 이유
- 실행 대조: 개발 서버에서 실제로 돌려, 실행된 코드가 그 기능의 코드 안에 있는지

어긋나면 B-1~B-4의 규칙을 고쳐 다시 뽑는다.

**B-6. 뜻.** 코드 그래프를 받은 컨텍스트가 기능 한 줄과 테이블·컬럼·이벤트·파라미터 뜻을 쓴다. 이 결과는 뜻 파일에 두고, 스크립트가 뽑은 파일과 따로 둔다.

**B-7. 추정 문서.** B-1~B-6을 하지 않은 새 코드 시선의 컨텍스트가 한다.
- 입력: 임시 그래프 B의 코드 층.
- 입력에서 제외: A의 결과.
- 결과물: 화면설계서, 정책, 유저 활동, 상위 문서. 코드만 보고 쓴 추정이라고 표시한다.

**B-8. 적재.** 코드 그래프, 기능, 뜻, B-7의 추정을 임시 그래프 B에 넣는다.

## C. 기획안

통합 시선의 컨텍스트가 한다.

**C-1. 기준.** 기존 기획안이 있으면 그것이 기준이다. 정의서의 문서 형식으로 옮기고, 옮기며 빠지는 내용은 빠졌다고 적는다. 없으면 A-4·B-7의 추정이 기준이다.

**C-2. 통합.** 기준 기획안과 A·B를 모두 읽고 한 사람이 쓴 기획안처럼 하나로 쓴다.
- 매칭: 화면은 주소와 상태, 화면요소는 같은 화면에서 같은 기능을 일으키는 것, 나머지는 이름과 내용.
- 매칭된 쌍마다 다른 곳은 코드·기획 자료·실행 환경을 확인해 무엇이 맞는지 정하고 근거를 적는다.
- 유저 쪽 글(문제, 목표, 얻는 것, 저니)은 A를, 구현 사실(기능, 화면요소 ↔ 기능, 정책이 걸리는 곳)은 B를 기준으로 한다. 의도는 기획안에서 가져오고, 실제와 다르면 다르다고 적는다.

**C-3. 흐름대로 써 보기.** 처음 온 유저 시선의 새 컨텍스트가 한다.
- 입력: 화면마다 "이 화면은 무엇을 하는 곳인가" 한 줄, 유저 활동의 유저플로우.
- 입력에서 제외: 화면설계서 전체, 그림, 탐색 기록, 코드.
- 결과물: 글대로 됐는지, 글로는 쉬웠는데 화면에서 어려웠던 곳.

**C-4. 반영.** C-3의 결과로 기획안을 고친다. 제품 판단이 필요한 것은 사용자 확인 목록에 올린다.

**C-5. 적재.** 제품코어, 유저저니, IA, 유저 활동, 화면, 정책을 임시 그래프 C에 넣는다.

## D. 합치고 실제와 대조

통합 시선의 새 컨텍스트가 한다. 입력은 A·B·C의 결과 전부와 실제 서비스다.

**D-1. 합치기.** 같은 값끼리 매칭한다: 요청(메서드·주소) ↔ 기능 ID, 화면 주소 ↔ 라우트, 문서에 적힌 ID ↔ 그 노드. 가리킨 노드가 없으면 실패다. 매칭되지 않은 것을 목록으로 만든다.

**D-2. 요청 대조.** A의 조작 기록과 B의 기능 → 프론트 코드를 맞춘다.
- 실제로 나갔는데 그 조작의 코드가 그 기능의 코드에 없다: B의 빠짐
- 기능의 프론트 코드에 있는데 한 번도 안 나갔다: 죽은 코드이거나 A가 못 간 상태

**D-3. 실제 물음.** 실제 물음으로 유저 활동 → 화면요소 → 기능 → 코드 → DB를 따라가, 그래프의 답이 실제와 같은지 본다. 노드 수와 파서 통과는 완료 기준이 아니다.

**D-4. 정합성 검사.** 정의서의 정합성 검사를 돌리고, 검사에 걸린 항목이 실제로도 그런지 본다.

**D-5. 실제와 다르면**
- 근거로 무엇이 맞는지 정해지면: 원본(문서, B의 규칙)을 고치고 그 층을 다시 적재해 다시 합친다.
- 제품 판단이 필요하면: 사용자 확인 목록에 올린다.

## 결과 확인

HEAD가 한다.
- 합격 기준은 무작위 표본과 검사 목록이다.
- 대표가 아닌 노드를 몇 개 골라 그래프에서 꺼내 원본과 대조한다.
- 같은 단계를 고쳐 다시 할 때는 그 단계를 한 컨텍스트를 이어서 쓴다. 검수, C, D는 다른 컨텍스트가 한다.

## 조회

다 만든 그래프를 기획·개발에서 쓰는 법이다.

- **기능 하나 조회:** 그 기능의 처리 코드에서 시작해 call·framework-invoked·callback으로 도달하는 코드를 들여쓰기 트리 하나로 보여 준다. 코드 줄마다 아래에 그 코드의 read / write, 외부 연결, navigate를 붙인다. 다른 기능의 처리 코드, 다른 페이지 코드, re-render 대상에 도달하면 이름만 표시하고 더 펼치지 않는다. 여러 번 나오는 코드는 처음 한 번만 펼친다.
- **유저 쪽에서 코드까지:** 유저 활동 → 화면요소 → 기능 → 코드 → DB 순서로 연결을 조회한다.
- **원본 읽기:** 조회한 노드의 문서 위치, 파일과 줄 범위로 원본을 연다. 답은 원본을 읽은 뒤에 한다.
- **경로 질의:** 한 단계씩 조회한다. 그래프 DB에서 길이를 정하지 않은 경로 질의는 모든 경로를 늘어놓아 서버를 멈출 수 있다.
