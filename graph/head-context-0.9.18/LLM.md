# head-context 0.9.18 제품 그래프 — LLM용 조회 안내

이 그래프는 head-context 플러그인(head-agent-core commit `043ffdb`, `packages/context`)을 노드와 연결로 기록한 인덱스다. 물음을 받으면 그래프로 볼 곳을 좁히고, 그래프가 가리킨 원문을 읽은 뒤 답한다.

## 시작

이 파일이 있는 폴더에서 실행한다. Python 3 표준 라이브러리만 쓰고, 읽기만 한다.

```
python3 hc_graph.py overview
```

노드 종류별 수, 유저가 받는 글의 묶음, 유저 활동 목록, 기능 목록이 나온다. 처음 한 번 보고 물음에 맞는 명령으로 내려간다.

## 노드 종류

이 플러그인에는 그림으로 된 화면이 없다. 그래서 "화면"은 유저가 받는 출력 한 종류를 뜻한다. 유저는 사람이거나 그 사람이 쓰는 AI agent다.

| 종류 | 이 그래프에서 무엇인가 | ID 예 |
|---|---|---|
| 제품코어 | 이 플러그인이 무엇이고 누구를 위한 것인가 | `product:head-context` |
| 유저 활동 | 유저가 한 가지 일로 받아들이는 활동과 그 차례 | `ua.record` |

## 물음에 맞는 명령

| 물음 | 명령 |
|---|---|
| 이 기능을 고치려면 어디를 보나 | `feature tool:save` — 처리 코드에서 call·callback·framework-invoked로 닿는 코드 트리, 줄마다 읽고 쓰는 것 |
| 이 코드를 바꾸면 무엇이 걸리나 | `impact sessions.closeBranch` — 그 코드에 닿는 기능과 그 기능의 화면·정책 |
| 유저가 이 일을 할 때 무엇이 어떻게 도나 | `user ua.resume` — 유저 활동 → 화면요소 → 기능 → 처리 코드 → 데이터 |
| 이 출력은 무엇이고 어느 기능이 내나 | `screen STA-04` — 화면 정책(표시 정책)과, 화면설계서 글이 이름으로 가리킨 처리 정책(그 정책을 지키는 기능과 함께)도 보인다 |
| 무엇이 정해져 있는지 한 번에 | `checks` — 어느 기능에서도 닿지 않는 코드, 정합성 검사 목록 |
| 이 동작은 정해 둔 규칙인가 | `policy <정책 ID>`, 또는 `find <낱말> --type 정책` — 처리 정책은 지키는 기능과, 그 정책을 글로 가리키는 화면을 보인다 |
| 이름만 알 때 | `find 압축` (`--type 화면요소`처럼 좁힐 수 있다) |
| 노드 하나의 속성과 연결 전부 | `show TOL-03#1` |
| 원문 읽기 | `source <ID>` — 문서 노드는 원문 글, 코드 노드는 파일·줄. `--repo <head-agent-core>/packages/context`를 주면 그 줄을 보인다 |
| 직접 SQL | `schema`로 테이블 꼴을 보고 `sql "SELECT …"` (읽기 전용) |

코드 노드는 ID, `code:`를 뗀 꼴, 함수 이름, 한정 이름 어느 것으로 줘도 된다. 이름이 겹치면 후보를 보이고 멈춘다. 결과는 글로만 나온다. 표로 받으려면 `sql "SELECT …"`를 쓴다.

## 답하는 법

1. 그래프로 관련 노드와 파일·줄을 찾는다.
2. 그 원문을 읽는다. 코드는 `git -C <head-agent-core> show 043ffdb:packages/context/<파일>`로 읽는다. 작업 트리가 다른 판이면 줄 번호가 어긋난다.
3. 원문을 읽은 뒤에 답한다. 그래프는 찾아가는 지도이고, 지금 동작을 정하는 것은 원문이다.
4. 그래프에서 아무것도 나오지 않아도 그것이 없다는 뜻은 아니다. 원문을 직접 찾는다.

## 연결의 근거

- 코드끼리의 연결은 스크립트가 구문 트리와 TypeScript 타입 검사기로 뽑았다. 따라가는 종류는 call(부름), callback(함수를 값으로 넘김), framework-invoked(경로로 실행)다.
- 화면요소 ↔ 기능 연결은 두 근거뿐이다. `실행 R번호`는 플러그인을 실제로 돌린 출력에서 그 글이 나온 것이고, `코드 파일:줄`은 그 글을 만드는 코드 자리다. 연결의 `근거` 속성에 적혀 있다.
- 유저 활동의 `실제와 다름` 줄은 정해 둔 규칙을 시험 한 번에서 agent가 어긴 사실이다. 경향이 아니다. `관찰` 줄은 규칙 위반이 아닌 사실이다.

## 한계

- `impact`에 나오는 화면요소는 그 기능이 내는 출력 후보 전부다. 그 코드를 바꿀 때 실제로 바뀌는 글은 코드 가지를 읽어 정한다.
- 플러그인이 따로 띄우는 스크립트 안으로는 따라가지 않는다. 그 자리에서 "경계에서 멈춤"을 보인다.
- 값을 읽기만 하는 참조(상수 읽기 등)는 잇지 않았다. 상수를 바꿨을 때의 영향은 `find`나 원문 검색으로 찾는다.
- 유저 활동은 0.9.5 때 Claude Code로 실제로 써 보고 썼고, 0.9.10·0.9.15·0.9.17·0.9.18에서는 다시 써 보지 않았다(뒤 판에서 바뀐 것은 해당 줄에 적었다). Codex와 OpenCode 쪽은 실제 앱 없이 훅·도구 서버·플러그인 훅 함수를 직접 돌린 출력과 코드로 썼다.
- Antigravity 쪽(0.9.11~)도 실제 agy 없이 훅(`scripts/antigravity-hook.mjs`)과 도구 서버를 agy가 주는 꼴의 입력으로 직접 돌린 출력(R159~R232)과 코드로 썼다. 서브에이전트는 실측(agy 1.5.13의 `invoke_subagent` self·research)에서 본 입력 꼴만 따랐다. ACP 깨우기가 `started`를 돌려주는 경우는 실제 ACP 프로세스가 있어야 해서 run에 없다. 그 연결은 코드와 시험으로만 이었다. 터미널 깨우기의 `started`(R273~R275)는 가짜 agy 프로세스로 본 것이다.
- Antigravity의 깨우기 신호(loopback `SendAgentMessage`)와 서브에이전트 판정(agy 대화 폴더의 부모 메시지)은 agy의 공개되지 않은 내부 통로·파일에 기댄다. agy가 꼴을 바꾸면 깨우기는 `queued`로, 서브에이전트는 사람 대화로 다뤄진다. 0.9.18 터미널 깨우기는 여기에 셋을 더 기댄다: agy가 모델 셸에만 넘기는 LS 주소·열쇠 환경 변수, agy 내부 잠금 파일(`~/.gemini/antigravity-cli/presence/<ID>.lock`)을 그 pid가 열어 두었는지(Linux `/proc/<pid>/fd`, Mac `lsof` — Mac 미확인), 도구 전 훅의 `auto_approve`. 깨우기 열쇠 기록과 잠금 파일 자리는 홈 아래 고정이라 agy를 다른 데이터 폴더로 띄우면 늘 `queued`다. 도구 전 훅이 10초를 넘기면 agy가 그 셸 명령을 거절한다(셸 대체로도 못 막음).
- Antigravity 등록 파일(`${PLUGIN_DATA}/conversations/<ID>.json`, 칸 `cwd`·`checkpoint`·`parent`)은 그래프에 데이터 칸이 없다. 읽기·쓰기가 공용 도우미(readLoose·atomicJSON)만 거쳐 「.head/ 상태·기록·색인 파일」로 보인다. 위 공용 도우미 줄과 같은 한계다.
- 전역 `fetch`는 추출기가 접근 사실로 잡지 않는다. Antigravity language server로 가는 외부 연결 둘(ACP·터미널 신호)은 빌드가 손으로 이었다(build_graph.py MANUAL_OUTSIDE).
- 깨우기 열쇠 기록을 '없을 때만 만들기'(`openSync` 'wx')는 빌드의 API 표에서 읽기로 분류된다(claimAsk의 read 연결). 같은 함수의 write 연결(mkdirSync·writeSync)이 따로 있다.
- `실행 R번호`는 0.9.18 실행 기록 번호다. R112까지는 0.9.5와 같은 차례의 실행이다. R113~R139는 0.9.6~0.9.10에서 바뀐 동작, R140~R158은 0.9.10 독립 검수가 짚은 출력, R159~R232는 Antigravity(0.9.11~0.9.15, 서브에이전트 포함)를 보려고 더한 실행이다(R221~R232는 독립 검수가 짚은 출력: 등록 안 된 대화의 도구 10개, 편지함 폴더를 읽을 수 없는 Antigravity·Codex). R233~R255는 0.9.16·0.9.17 변경(컴팩트 뒤 먼저 할 것, Claude 프로그램 실행의 연결 안 됨 안내 없음, 짧은 말의 said, 작업 세션 머리 자르기)을 보려고 더한 실행이다. R246은 출력이 아니라 presence를 읽은 측정값이다. R256~R299는 0.9.18 터미널 깨우기를 이름이 agy인 가짜 node 프로세스로 본 실행이다(실제 agy가 아니다. 실제 터미널 agy는 0.9.18 실제 확인 1~8). R192는 세 도구 서버의 serverInfo 판이 plugin.json 판과 같은지 기록한다.
- 글을 만드는 코드 자리로 이은 연결(`코드 파일:줄`)은 그 자리가 든 함수에 닿는 기능을 잇는다. 화면설계서가 그 화면요소를 내는 기능을 적어 두었으면 그 기능만 잇는다. 적어 두지 않은 화면요소는 실제로는 그 글을 내지 않는 기능이 붙을 수 있다.
- 출력 글이 같아 실행으로 맞았지만 그 화면요소가 아닌 연결 둘은 빌드가 이름으로 뺐다(STA-01#3 ← Claude 시작 훅·setup).
- 실행으로 이은 연결(`실행 R번호`)은 실행한 기능에만 붙는다. 화면설계서가 그 화면요소를 내는 기능을 적어 두었으면, 그 기능 가운데 그 글의 코드 자리에 닿는 것을 코드 연결로 보탠다(예: 잠금 실패 ERR-01#13 ← 잠금을 쥐는 도구 9개, 기록 알림 CMN-03#1, 훅 실패 ERR-04). 적어 두지 않은 화면요소는 실행하지 않은 기능이 같은 글을 내도 이어지지 않는다. 그래서 어떤 글을 내는 기능을 전부 찾을 때는 그 글의 코드 자리를 `find`나 원문 검색으로도 본다.
- 데이터(`data:…`) 연결은 파일 시스템 호출이 든 자리로 대상을 정한다. 한 파일 안에서 대상이 다르면 줄 단위로 나눴고(project.mjs), 호스트 대화 기록 끝을 읽는 도우미(readTail)는 부르는 쪽에 이었다. 여러 곳에 쓰는 공용 도우미(atomicText·atomicJSON·optionalRead·locked)는 나누지 않아, 설정 파일이나 CLAUDE.md에 쓰는 것도 `.head/` 데이터로 보인다.
- `source --repo`는 준 폴더의 파일이 그래프를 만든 커밋의 파일과 다르면 그렇다고 알린다. 그때 줄 번호는 믿지 말고 `git show 043ffdb:…`로 읽는다.
